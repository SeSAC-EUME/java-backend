# EUME 추가 기능 개요 정리 (요약 버전)

> 이 문서는 `etc/add-api` 폴더에 개별로 정리된 문서들을 하나로 묶어,
> **상세 설계에 들어가기 전, 어떤 기능들을 추가 구현할지**를 한눈에 정리한 개요 문서입니다.
> 각 항목은 "무엇을 할 수 있어야 하는지" 수준까지만 적고, 세부 스펙/에러코드는 기존 구현 계획서(002/003 등)와 개별 플랜 문서에서 다룹니다.

---

## 1. User 영역 추가 기능

### 1.1 사용자 계정 비활성화/탈퇴

- **목적**
  - 사용자가 스스로 서비스 이용을 중지하거나, 계정을 완전히 탈퇴할 수 있도록 함.
  - 비활성화된 계정에 대해서는 로그인/서비스 이용을 차단.

- **필요 기능**
  1. `EumeUser` 상태 전환
     - `userStatus` 를 이용해 `ACTIVE` ⇄ `DEACTIVATED` 전환
     - 필요 시 `DELETED` 등 추가 상태 고려
  2. 도메인 메서드
     - `deactivate()`, `activate()` (선택: `markDeleted()`)
  3. 서비스 계층
     - 로그인 유저 기준 비활성화/탈퇴 처리: `deactivateUser(String email)` 등
     - 처리 시 기존 `logout` 로직을 재사용하여 토큰/세션 만료
  4. 사용자 API
     - `POST /api/users/me/deactivate` : 자기 계정 비활성화 요청
     - (선택) `POST /api/users/me/withdraw` : 자기 계정 탈퇴 요청
     - 응답은 단순 성공 메시지 + 변경된 상태 정도로 가볍게
  5. 보안/에러 처리
     - `SecurityConfiguration` 에 경로 추가, JWT 필요
     - 비활성 계정 로그인 시 `U_****` 에러 코드로 거부

- **Google 소셜 로그인 연동 해제**
  - 비활성화/탈퇴 시, 저장된 Google 식별자(`providerId`)를 더 이상 로그인에 사용하지 못하도록 처리
  - (선택) 저장된 OAuth 토큰이 있다면 Google API 로 revoke 요청 검토
  - 동일 Google 계정으로 재가입 허용 여부/정책 별도 정의

## 2. Admin 영역 추가 기능

### 2.1 관리자 로그인 보완: 소속 기관 선택

- **목적**
  - 관리자 로그인 화면의 "소속 기관" 드롭다운을 실제 데이터와 연결.
  - 향후 기관별 권한/통계 분리를 위한 기반 마련.

- **필요 기능**
  1. 기관 목록 조회 API
     - `GET /api/admin/orgs` (인증 없이 호출)
     - 응답: `AdminOrgResponse(id, name)` 리스트
     - 기본 구현은 `Sigungu` 엔티티(`sido`, `sigungu`)를 활용하여 `"서울시 은평구"` 와 같은 이름 구성
  2. 서비스/Repository
     - `SigunguRepository.findAll()` 및 이를 감싸는 검색 서비스
  3. 확장 여지
     - 실제 기관(복지관, 센터 등)이 세분화되면 별도 `Organization` 엔티티 도입
     - `EumeAdmin` ↔ `Organization` 관계 및 기관별 권한 설계는 추후 단계에서 확장

---

### 2.2 Admin 이용자 관리 강화

기존 구현 계획서(002/003)에는 **목록 조회 + 상세 조회**가 이미 정의되어 있음. 여기에 화면 요구사항(이용자 관리 시안)을 맞추어 다음 기능을 추가로 구현한다.

- **기본 구조 재확인**
  - 목록: `GET /api/admin/users` (페이지네이션, 상태/검색어 필터)
    - 응답: `AdminUserListResponse` + `AdminUserResponse`
    - 테이블 표시용 핵심 필드만 포함 (id, email, 이름, 닉네임, 상태, 시군구명, 마지막 로그인일, 가입일 등)
  - 상세: `GET /api/admin/users/{userId}`
    - 응답: `AdminUserDetailResponse` + `AdminSigunguResponse`
    - profileImage, providerId, 생년월일, 성별, 전화번호, loginFailCount 등 민감/추가 정보는 여기서만 제공

- **추가로 구현할 기능**

1. **이용자 상태 변경 API**
   - 목적: 관리자가 특정 이용자를 **활성/비활성** 으로 전환할 수 있게 함.
   - 엔드포인트 예시:
     - `PATCH /api/admin/users/{userId}/status`
     - Request: `AdminUserStatusUpdateRequest(status: "ACTIVE" | "DEACTIVATED")`
   - 구현 포인트:
     - `EumeUser.userStatus` 와 `UserStatus` enum 을 일관성 있게 사용
     - 비활성화 시 User 로그인/토큰 발급 로직에서 차단되도록 연동
     - `EumeUserErrorCode` 컨벤션(`U_****`)에 맞는 에러 코드 추가

2. **이용자 목록 Excel/CSV 내보내기**
   - 목적: 현재 필터/검색 조건에 맞는 이용자 데이터를 파일로 추출.
   - 엔드포인트 예시:
     - `GET /api/admin/users/export?status=...&keyword=...`
   - 응답 방식 후보:
     - Excel 바이너리 (`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`)
     - 또는 CSV/JSON 후 프론트에서 파일 저장
   - 정책 포인트:
     - 최대 행 수 제한 여부, 기간 필터 추가 여부(예: 가입일 범위)

3. **추가 고려(선택)**
   - 목록 정렬 옵션 (최근 활동순, 이름순 등)
   - 위험도 컬럼이 필요하면, `AdminUserResponse` 에 위험도 점수/라벨 필드 추가 검토

### 2.3 Admin 보고서(리포트)

보고서 화면은 **여러 통계를 한 번에 모아보고, PDF/Excel 로 다운로드**하는 것이 목적이다. 구현 시점은 후순위이지만, 어떤 데이터가 필요할지 미리 정리해 둔다.

- **보고서에 포함할 데이터(기간 기준)**
  1. 이용자 활동 요약
     - 총/활성/신규 이용자 수, 평균 활동 시간
     - 일별 활성 이용자 수
  2. AI 대화 요약
     - 총 대화 수, 일평균 대화 수
     - 대화량이 많은 이용자 TOP N
  3. 감정 분석 요약
     - 정서적 주의가 필요한 이용자 수
     - 감정 점수 분포(매우 좋음~매우 우울)
  4. 긴급 상황 요약
     - 총 긴급 요청 수, 평균 응답 시간, 상태별 건수
  5. 일별 상세 테이블
     - 날짜별 활성 이용자 수, 대화 수, 긴급 요청 수, 평균 감정 점수 등

- **요약 데이터 조회 API**
  - `GET /api/admin/reports/summary?from=YYYY-MM-DD&to=YYYY-MM-DD&orgId=...`
  - 응답: `AdminReportSummaryResponse`
    - `userActivity`, `conversation`, `emotion`, `emergency`, `dailyStats` 등 서브 DTO로 구성
  - 구현 시, 기존 Repository(EumeUser, UserEmotion, 대화/긴급 엔티티)를 재사용하여 집계

- **파일 다운로드 API**
  - `GET /api/admin/reports/export?from=...&to=...&orgId=...&format=pdf|excel`
  - 내부에서 summary 집계 로직을 재사용한 뒤, 포맷에 따라:
    - PDF 템플릿 렌더링 → `application/pdf`
    - Excel 시트 생성 → `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`
  - 처리 시간이 길어질 경우, 추후 비동기 보고서 생성 + 상태 조회 API 로 확장 가능

## 3. 우선순위 정리

상세 기획/설계 전에, 실제 구현 관점에서 **우선적으로 가져갈 기능**과 **후순위 기능**을 나누면 다음과 같습니다.

1. **우선 구현 대상**
   - 사용자 계정 비활성화/탈퇴 (User 자기 계정 + Admin 쪽 상태 변경과 연계)
   - Admin 로그인 보완: 소속 기관 목록 조회 (`/api/admin/orgs`)
   - Admin 이용자 관리 강화
     - 목록/상세 조회 구현 상태 점검
     - 이용자 상태 변경 API
     - 이용자 데이터 Excel/CSV 내보내기

2. **후순위(데이터가 쌓인 뒤/운영 단계에서)**
   - Admin 보고서 요약/다운로드 (summary + export)
   - 대시보드/감정 분석/긴급 상황 상세 통계 등 시각화 중심 기능

이 문서는 "무엇을 만들지"를 빠르게 훑어보는 용도이며,
실제 개발에 들어갈 때는 각 항목을 기존 구현 계획서(002/003)와 매칭하면서 세부 스펙/에러코드/테스트 전략을 보완하면 됩니다.
